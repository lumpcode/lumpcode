# Website

Landing page, worker positioning, docs site, build and deploy (`packages/apps/website`).

- Positioning: Lumpcode is **the simplest way to set up software factories in your repo**; a **lump** is one software factory living in the repo, specific (one migration) or general (a spec backlog that keeps being fed), defined in code the user owns and commits like the rest of the repo. Keep "simplest" visible on the first screen (h1 `The simplest software factory` / `lives in your repo.`, kicker `Open source. You just need git and a CLI agent.`; meta title, README, CLI README, npm and GitHub descriptions say the same). Lead with **(micro) software factories as code**; the plural framing is **a fleet of micro software factories** (start with one, grow a fleet): a lump is a factory as code, committed like the rest. Git as the only state is said plainly (`Git is the only state`), still without the word git-first. The category is the headline, so the lede must give the mechanism right away (agent, a branch per piece of work, git only, no account/database/deploy) — never leave "software factory" as a bare buzzword. Review is the operator's choice: each branch is reviewed as a PR or merged by the operator's CI (e.g. a GitHub workflow enabling auto-merge on `lump/<name>/**`); Lumpcode itself never merges. Do not imply a "dark factory" (no review by design) or an end-to-end intake-to-deploy platform; Lumpcode stops at `git push`. Never write "localised" factories (reads as i18n); say "in your repo".
- Landing (`packages/apps/website`) is for a developer who has never heard of Lumpcode: headline category, then the lump definition, then when-to-use, then the loop, then git/agent specifics. A stranger should leave able to say: a lump is a software factory I commit to my repo; Lumpcode runs my coding agent through it and pushes a branch per piece of work that I review or my CI merges; everything is managed via git only. First screen uses agent, factory, branch, PR, git; define **lump** once as that factory; delay tick/daemon/context and the worker until after that. Hero kicker is a full sentence with a verb (`Open source. You just need git and a CLI agent.`), not a slogan. Hero shows an easy JSON start (valid `config.json` shape); the same CLI runs TypeScript, validation, and multi-lump pipelines. Workflow copy includes reviewing the PR and adjusting the branch before merge. Git-first means loops run, update, and remember from the project git repo, not an external database; do not claim there is no dashboard (a UI may come later and would read git). Keep landing copy short; later sections prove the hero, they do not repeat it. Landing diction: say **your git remote**, not `origin`, in prose; never mix **item** and **context** for the same thing — pick one noun, and introduce `context` late attached to the branch list (it collides with LLM context window), not in a hero lede. Keep the product noun **context** (do not rename to item/slice); teach it by labeling two similar blocks on the lump in view, not a glossary sentence. Hero (`exampleConfig` in `site.ts`) and `DOCS/start/first-pr.md` show the same nested beginner snippet (kept in sync by hand) (`prompt.promptTemplate` + `command` inside `prompt`, Vue-port body). Landing filename stays `.lumpcode/lumps/portToVue/config.json`; Get started still edits `.lumpcode/lumps/myFirstLump/config.json`. The flat top-level `command` / string `prompt` shorthand remains valid in the schema, but the site does not show it. Hero layout is load-bearing: h1 `.hero-line` spans must not wrap, the hero code snippet must fit with **no horizontal scrollbar** (shorten the snippet or trim horizontal padding rather than allowing a scroller), caption text over the lumpfish must stay legible against its dark square, and the hero plus the codebase→lump→branches stack must stay fully visible on a 13-inch MacBook with browser chrome (trim hero top padding rather than crop copy). Non-interactive feature/range cards must not look clickable (no hover affordance). Safety/trust points get their own labelled strip (now under "Factories as code."), not muted pills at the bottom of a section. Landing order: hero, statement band (`Start small, grow big.`), What you do (each step has a visual below it, data in `site.ts`: a TS `retryUntilGreen` config, a `StepTerminal` showing `lumpcode start` then `lumpcode transcript` on a worker clone, and a `StepPullRequest` card that ends Merged; the terminal is an illustration, not literal CLI output, so keep it close to real behavior: a laptop `run` in shared mode does not push), A fleet of micro software factories (a `For example` row of tiles plus a dashed `Your own flow` tile, so kinds read as examples, not modes: a lump is just code and Lumpcode only fixes the shape; then `Lumpcode is built by its own fleet.` with this repo's real `.lumpcode/lumps` tree and "close to half of the merged PRs came from lump branches"), Factories as code (lead says committed and reviewed like the rest; a 2x2 of exactly four points, keep it at four: `Your repo is the context`, `Git is the only state`, `Plug-and-run recipes`, `Use the agent you already have`. Repo-as-context means a lump runs inside the repo, so the agent has the team's skills, AGENTS.md, docs and conventions from the first run, nothing to upload or index; the hero's second lede says it too; + safety strip), You could script this (four cards, CLI-only: resuming, blast radius, clean workspaces, nothing left running), worker, install. Validation and retry until green come from `@lumpcode/recipes`, not the CLI: never present them as a CLI feature. Use the package's own two words precisely: a **recipe** is a whole ready-made factory in one function call (`featureBacklog({…})`: ticket folders → requirements, tests, code, checks; this repo's backlog lanes are each one recipe call), described as **plug-and-run**; the **kit** holds the smaller pieces (`retryUntilGreen`, `openPrPostTeardown`). Never call a kit helper "a recipe". In landing prose, PR opening is "opened automatically after the push" (no jargon). The fleet line says autoTriage feeds four backlogs (backlog, docs, qol, bugfixes). **Never write context = one file, or one context = one PR**: a context is a unit of work (a file, a group of files, a ticket) per `DOCS/start/terms.md`, and `numberOfContextsPerBranch` groups several onto one branch (the codemod example in `DOCS/examples/sweeps.md` uses 10 per PR). Landing copy says a run pushes a branch **you review as a PR or let your CI merge** — the CLI stops at `git push`; opening the PR is the opt-in `@lumpcode/recipes` `openPrPostTeardown` helper (JS/TS config + `gh`), never a built-in, so never write that Lumpcode or the daemon "opens pull requests", and never imply the operator must open them by hand either: say "open it yourself, or let a recipe open it after the push" (landing step 3, worker `Branches arrive`, and the step 3 PR card's first event) (idea `first-class-open-pr` tracks moving it into the CLI; restore that copy only when it ships). Daemon section is "Branches arrive", not "Pull requests arrive". Landing copy also states "one context per branch by default; group several when the diffs are small". The landing answers the "you could script this" objection with what the CLI itself does (resuming; blast radius as one PR you adjust or close, not a 200-file diff; clean workspaces; nothing left running) — that section is what separates a lump from a bash loop.
- Landing positioning: never define Lumpcode by one axis of work — definition sentences (h1, lede, the "what is a lump" line) stay axis-free and show the range (`Make it specific to one migration or general enough to take a spec backlog that never stops growing.`) while example slots may stay codemod-first; avoid copy implying the repeated work is the *same* task (`Lumpcode runs the whole list`, not "runs the other two hundred"). Never write **git-first** in landing copy (zero occurrences is deliberate) — express it only as consequences the reader feels: resuming from the remote, no database, nothing to deploy or register, and changing a loop is a pull request your team reviews like any other code (git gates the loop config, not just agent output). Never write **graph** (insider / LangGraph-adjacent) — say concretely that each item can run several prompts in order, gated on your build or tests and retried with the failure output (`getValidationLoopSteps` / `retryUntilGreen` in `packages/recipes/src/kit/`). Breadth is proved by artifacts, not adjectives: the heterogeneous `lumpsTree` code window sits immediately after the "What you do." usage section — beware concreteness asymmetry, an example rendered with a config snippet + branch window becomes the de-facto definition while examples merely listed as pills do not register. The loop itself is shown as codebase (two contexts) → lump → branches, not lump-only.
- Worker positioning: first-run is one PR by hand (`lumpcode run` on the laptop); intended use is a **worker** (`lumpcode start` on a second clone — another folder is enough; an always-on box is the upgrade). Author and merge on the laptop; the worker pushes branches. Do not make the worker the install path — make it the reason to stay. On the landing, "What you do." step 2 is `Start a worker` (`lumpcode start`, watched with `lumpcode transcript`, since `start` detaches) with `lumpcode run` named as the one-pass try; the later `#worker` section is titled `Built to run without you.` and has no steps of its own (they duplicated step 2): copy (try/use line, always-on machine, a pushed lump is picked up on the next pass) plus the looping branch window. Say each claim once: the hero keeps `No account, no database, no backend: git is the only state.` (not "nothing to deploy": the recommended worker runs on an always-on machine; what Lumpcode lacks is a service of its own) and leaves "changing a factory is a pull request" to Factories as code; the statement band names the two commands (`lumpcode setup` and `lumpcode run`). Step visuals play fast (~170ms per line) so a normal scroll never shows an empty card. Never contrast CLI vs worker: both use the CLI. Try/use is a one-off run (`lumpcode run`, shared) vs a dedicated worker (`lumpcode start`). User-facing name is **worker** (secondary: **Leave it running**); "dedicated daemon", `shared` / `dedicated` / `global`, and "tick" are operator words — details next to config, never titles, nav, or hero copy. URL is `/docs/start/worker`. `/docs/start/first-pr` is a single path to a first PR (not a mode picker); 301 `/get-started` → `/docs/start/first-pr` and `/get-started/worker` → `/docs/start/worker`. The worker is the payoff after that first PR, not a top tab. `#worker` is a second hero (do not move it above the first lump explanation): start with a second clone on this machine, and name an always-on remote machine as the best setup Lumpcode is built for. ## Build and deploy

- Public marketing site, Nuxt 4 + Vue 3 + Vite; does not use `@lumpcode/ui`; no-mouth logos from `assets/`; `npm run website`; `npm run website:deploy` generates and uploads to Cloudflare Pages project `lumpcode`; GitHub Action `.github/workflows/deploy-website.yml` runs that on push to `main` only when `packages/apps/website/**`, `packages/apps/cli/DOCS/**`, `packages/apps/cli/package.json` (the site shows the CLI version from it via `app/utils/version.ts`, in the footer and at the bottom of the docs sidebar), the published CLI `lumpConfig.schema.json` / `daemonConfig.schema.json` / `projectConfig.schema.json` / `localConfig.schema.json`, recipes `backlogDesc.schema.json` / `featureBacklogDesc.schema.json`, or the workflow file change (`workflow_dispatch` for a manual run; needs `CLOUDFLARE_API_TOKEN` + `CLOUDFLARE_ACCOUNT_ID` repo secrets); canonical `siteUrl` is `https://www.lumpcode.com`; `nuxt generate` copies CLI `lumpConfig.schema.json` / `daemonConfig.schema.json` / `projectConfig.schema.json` / `localConfig.schema.json` and recipes `backlogDesc.schema.json` / `featureBacklogDesc.schema.json` to gitignored `public/schemas/` for `$schema` URLs (docs keep the apex `https://lumpcode.com/schemas/...`); pages: `/` landing, `/docs/start/overview` operator manual (301 `/docs` → overview), `/docs/start/first-pr` first PR (one-run on the laptop), `/docs/start/worker` worker (`lumpcode start` on a second clone) — first PR is not a mode picker; worker is the intended-run payoff after the first PR; worker page assumes committed `.lumpcode/` and points back to first PR; user-facing labels Worker / Leave a worker running; `CodeWindow` snippets include the file path and use local teal/white syntax highlighting (`highlightSnippet.ts`)
- Theme and motion: light/dark via `data-theme` on `<html>`, set before paint by `themeBootScript` (`app/utils/site.ts`; stored choice under `lumpcode-theme`, else system). Colors are tokens on `:root` / `:root[data-theme='light']` in `main.css`; the worker dashboard (`packages/apps/dashboard/src/page.ts` `ROOT_CSS`) holds a verbatim copy of the first `:root` block and `page.unit.test.ts` fails if they differ, so re-sync it (and any token it uses, e.g. `--surface-solid`) whenever the website tokens change; never hardcode a color in `docs.css` or components. Code windows and the worker `.ocean` panel stay dark in both themes (they re-scope the tokens). Fish colour morphs (`fish-aqua`, `fish-ocean`, `fish-deep`, `fish-coral`, `fish-amber`, `fish-violet`, `fish-olive`) override the `--fish-*` tokens; keep teal the majority. The opening school uses only teal and cold shades, always the same mix (8 teal, 2 ocean, 1 aqua, 1 deep, shuffled per load in `Aquarium.vue`); warm colours (coral, amber, violet) are for the slow background fish only, since fast warm fish are hard on the eye. Some fish carry cargo in their mouth (`FishCargo.vue`, picked client-side in `utils/fishCargo.ts`: a JS/TS file or a generic diff file, a 6% chance of a cake, burger or pizza; Lumpcode is mostly JS/TS today, so keep file types to that); only the slow background fish carry it (the opening school carries nothing) and they re-pick it each crossing. No background grid. Header/footer brand is the SVG `Lumpfish` + wordmark (`BrandMark.vue`), not the white-text PNG lockup, so it reads in light mode. Landing motion (school of lumpfish crossing once per browser session — `sessionStorage` key `lumpcode-school-seen` — **behind** the hero copy and cards, never in front of text, and removed from the DOM ~9s after load so nothing keeps animating, drifters, `data-reveal` scroll fades via `useReveal`) must stay decorative and stop under `prefers-reduced-motion`; `[data-reveal]` hides content only when `html.js` is set.
