# Website

Landing page, worker positioning, docs site, build and deploy (`packages/apps/website`).

- Landing (`packages/apps/website`) is for a developer who has never heard of Lumpcode: lead with the job, then when-to-use, then the loop, then git/agent specifics — not category branding. A stranger should leave able to say: it runs my coding agent through a big campaign, one reviewable PR at a time, and everything is managed via git only. First screen uses agent, campaign, PR, git; define **lump** once as that campaign; delay tick/daemon/context and the worker until after that. Hero kicker is a full sentence with a verb (`You just need git and a CLI agent`), not a slogan. Hero shows an easy JSON start (valid `config.json` shape); the same CLI runs TypeScript, validation, and multi-lump pipelines. Workflow copy includes reviewing the PR and adjusting the branch before merge. Git-first means loops run, update, and remember from the project git repo, not an external database; do not claim there is no dashboard (a UI may come later and would read git). Keep landing copy short; later sections prove the hero, they do not repeat it. Landing diction: say **your git remote**, not `origin`, in prose; never mix **item** and **context** for the same thing — pick one noun, and introduce `context` late attached to the branch list (it collides with LLM context window), not in a hero lede. Keep the product noun **context** (do not rename to item/slice); teach it by labeling two similar blocks on the lump in view, not a glossary sentence. Hero (`exampleConfig` in `site.ts`) and `DOCS/start/first-pr.md` show the same nested beginner snippet (kept in sync by hand) (`prompt.promptTemplate` + `command` inside `prompt`, Vue-port body). Landing filename stays `.lumpcode/lumps/portToVue/config.json`; Get started still edits `.lumpcode/lumps/myFirstLump/config.json`. The flat top-level `command` / string `prompt` shorthand remains valid in the schema, but the site does not show it. Hero layout is load-bearing: h1 `.hero-line` spans must not wrap, the hero code snippet must fit with **no horizontal scrollbar** (shorten the snippet or trim horizontal padding rather than allowing a scroller), caption text over the lumpfish must stay legible against its dark square, and the hero plus the codebase→lump→branches stack must stay fully visible on a 13-inch MacBook with browser chrome (trim hero top padding rather than crop copy). Non-interactive feature/range cards must not look clickable (no hover affordance). Safety/trust points get their own labelled strip after the band, not muted pills at the bottom of a section. **Never write context = one file, or one context = one PR**: a context is a unit of work (a file, a group of files, a ticket) per `DOCS/start/terms.md`, and `numberOfContextsPerBranch` groups several onto one branch (the codemod example in `DOCS/examples/sweeps.md` uses 10 per PR). Landing copy says a run pushes a branch **you open as a PR** — the CLI stops at `git push`; opening the PR is the opt-in `@lumpcode/recipes` `openPrPostTeardown` helper (JS/TS config + `gh`), never a built-in, so never write that Lumpcode or the daemon "opens pull requests" (idea `first-class-open-pr` tracks moving it into the CLI; restore that copy only when it ships). Daemon section is "Branches arrive", not "Pull requests arrive". Landing copy also states "one context per branch by default; group several when the diffs are small". The landing answers the "you could script this" objection (resuming; blast radius as one PR you adjust or close, not a 200-file diff, with the first PR showing if the prompt needs tweaking; validation/retry; unattended) — that section is what separates a lump from a bash loop.
- Landing positioning: never define Lumpcode by one axis of work — definition sentences (h1, lede, the "what is a lump" line) stay axis-free (`Some work is too big for one chat: a migration, a ticket backlog, a test suite to build out.`) while example slots may stay codemod-first; avoid copy implying the repeated work is the *same* task (`Lumpcode runs the whole list`, not "runs the other two hundred"). Never write **git-first** in landing copy (zero occurrences is deliberate) — express it only as consequences the reader feels: resuming from the remote, no database, nothing to deploy or register, and changing a loop is a pull request your team reviews like any other code (git gates the loop config, not just agent output). Never write **graph** (insider / LangGraph-adjacent) — say concretely that each item can run several prompts in order, gated on your build or tests and retried with the failure output (`getRecursiveSteps` / `retryUntilGreen` in `packages/recipes/src/kit/`). Breadth is proved by artifacts, not adjectives: the heterogeneous `lumpsTree` code window sits immediately after the "What you do." usage section — beware concreteness asymmetry, an example rendered with a config snippet + branch window becomes the de-facto definition while examples merely listed as pills do not register. The loop itself is shown as codebase (two contexts) → lump → branches, not lump-only.
- Worker positioning: first-run is one PR by hand (`lumpcode run` on the laptop); intended use is a **worker** (`lumpcode start` on a second clone — another folder is enough; an always-on box is the upgrade). Author and merge on the laptop; the worker pushes branches. Do not make the worker the install path — make it the reason to stay. Never contrast CLI vs worker: both use the CLI. Try/use is a one-off run (`lumpcode run`, shared) vs a dedicated worker (`lumpcode start`). User-facing name is **worker** (secondary: **Leave it running**); "dedicated daemon", `shared` / `dedicated` / `global`, and "tick" are operator words — details next to config, never titles, nav, or hero copy. URL is `/docs/start/worker`. `/docs/start/first-pr` is a single path to a first PR (not a mode picker); 301 `/get-started` → `/docs/start/first-pr` and `/get-started/worker` → `/docs/start/worker`. The worker is the payoff after that first PR, not a top tab. `#worker` is a second hero (do not move it above the first lump explanation) and must not imply a second computer. Worker page is an unnumbered day-in-the-life picture then a single numbered setup — do not run `project-setup` on the worker; the dedicated wipe warning sits next to `mode: dedicated`. `GuidePathNav` is a sequence (First PR → Leave a worker running), not a fork. Footer/nav: Dedicated daemon → Worker.
- Get started (`/docs/start/first-pr`) and worker (`/docs/start/worker`) use the **docs layout** (sidebar, search, pager, TOC). Skip link on first PR is `Already ran a lump locally? Try the worker.` Split 2. Install the CLI (runs a lump) from 2b. optional `/lumpcode` skill — it helps the user's own editor agent write and update lumps, not the agent that runs inside a lump. `CodeWindow` snippets stay syntax-highlighted for readability (teal keys/commands, white values), not monochrome. `GuidePathNav` is a sequence (First PR → Leave a worker running), not a fork. Get started CTAs (header, landing, footer; `docs.getStarted`) go to `/docs/start/first-pr`, never a hub (`/docs`, `/docs/start`, `/docs/get-started`) — do not add a third Get started URL or a hub page. Header Docs → `/docs/start/overview` and stays active on all `/docs` including first-pr/worker. All `/docs` paths use the docs layout (sidebar); `docs-layout.global.ts` forces it because `definePageMeta` can drop on HMR. On mobile, the docs sidebar toggle is a sticky navbar burger icon (not Menu/Close text); search is inside the opened drawer, without Ctrl/Cmd+K. Page kicker is `Docs/<section>` (e.g. `Docs/Start`), not `Tutorial`. Start sidebar order: Overview, First PR, Worker, Watch it work (dashboard/transcripts/logs), Core terms, How a run works; then an **Examples** section (`examples/`: overview picker, sweeps, issue-queues, backlogs, pipelines, building-blocks — patterns abstracted from real lumps, client material anonymized) before Author. First PR keeps the Vue-port snippet but tells the reader to change paths to files in their repo (or keep setup's README stub); setup asks primary branch and mode (pick shared); `lump-plan --contexts --prompts` before re-running; git identity required; commit and push `.lumpcode/` before the worker page. Worker requires git `user.name`/`user.email` and, for TypeScript lumps, `@lumpcode/cli-utils` + `@lumpcode/recipes` in the project `package.json`.
- Docs (`/docs` 301 → `/docs/start/overview`): **single source** — the website renders `packages/apps/cli/DOCS/<section>/<page>.md` directly (`import.meta.glob` in `loadDocs.ts`; top-level DOCS files like `README.md`, `publishing.md`, and old flat-name redirect stubs are GitHub-only). Each page starts `# Title` then a plain lead paragraph (used as the description); no frontmatter. Write GitHub-relative links (`../author/contexts.md#ordering`); `docsHref` in `renderMarkdown.ts` rewrites them to `/docs/...` routes and anything else to GitHub URLs; `slugify` matches GitHub anchors, so avoid em dashes in headings. Deploy workflow path filter includes `packages/apps/cli/DOCS/**`. Search (`docsSearch.ts`) indexes h2/h3 sections, ranks title > heading > body with word-boundary matching, small synonym map, AND then OR fallback, ≤3 hits per page, highlighted snippets; it keeps fenced-code and backtick identifiers (API names like `commandFn` must stay searchable); header/footer Docs links go to overview. Rewrite for scanning: job first, examples before exhaustive tables, worker-facing titles (`daemon-*` only as CLI names). Do not document `supervise` as an operator command. Do not write that Lumpcode opens pull requests (opt-in `openPrPostTeardown`). Overview: no account and no database; never "no dashboard". Hook signatures live at `/docs/config/types`. `command` is tag, lump-relative file, or inline `CommandFn` (JS/TS; return nothing to skip). How a run works starts at the procedure (loop engineering stays in root/CLI README + `start/terms.md`). Old flat `/docs/<page>` URLs, `/docs`, `/docs/start`, and `/docs/get-started` (plus `/docs/get-started/*`) 301 to the nested paths via generated `public/_redirects` (gitignored, same as sitemap; Cloudflare status is `301`, not Netlify `301!`); emit a trailing-slash twin for each source. The docs catch-all (`pages/docs/[[...slug]].vue`) must honor `docsRedirects` so `/docs/get-started` 301s to first-pr instead of 404. In-app links use canonical paths, not the old URLs. Config sidebar order: Lump config, Project, Local, Daemon files, Advanced, Types. The **worker** is the dedicated machine; a **daemon** is a scheduler on it (`--daemonId`, `.lumpcode/daemons/`). Do not call the machine a daemon or a file-launched process a worker. Daemon-file docs live at `/docs/config/daemons` (page title **Start daemons from git**), not on the Worker getting-started page (that page links there at the end).

## Build and deploy

- Public marketing site, Nuxt 4 + Vue 3 + Vite; does not use `@lumpcode/ui`; no-mouth logos from `assets/`; `npm run website`; `npm run website:deploy` generates and uploads to Cloudflare Pages project `lumpcode`; GitHub Action `.github/workflows/deploy-website.yml` runs that on push to `main` only when `packages/apps/website/**`, `packages/apps/cli/DOCS/**`, `packages/apps/cli/package.json` (the site shows the CLI version from it via `app/utils/version.ts`, in the footer and at the bottom of the docs sidebar), the published CLI `lumpConfig.schema.json` / `daemonConfig.schema.json` / `projectConfig.schema.json` / `localConfig.schema.json`, recipes `backlogDesc.schema.json` / `featureBacklogDesc.schema.json`, or the workflow file change (`workflow_dispatch` for a manual run; needs `CLOUDFLARE_API_TOKEN` + `CLOUDFLARE_ACCOUNT_ID` repo secrets); canonical `siteUrl` is `https://www.lumpcode.com`; `nuxt generate` copies CLI `lumpConfig.schema.json` / `daemonConfig.schema.json` / `projectConfig.schema.json` / `localConfig.schema.json` and recipes `backlogDesc.schema.json` / `featureBacklogDesc.schema.json` to gitignored `public/schemas/` for `$schema` URLs (docs keep the apex `https://lumpcode.com/schemas/...`); pages: `/` landing, `/docs/start/overview` operator manual (301 `/docs` → overview), `/docs/start/first-pr` first PR (one-run on the laptop), `/docs/start/worker` worker (`lumpcode start` on a second clone) — first PR is not a mode picker; worker is the intended-run payoff after the first PR; worker page assumes committed `.lumpcode/` and points back to first PR; user-facing labels Worker / Leave a worker running; `CodeWindow` snippets include the file path and use local teal/white syntax highlighting (`highlightSnippet.ts`)
