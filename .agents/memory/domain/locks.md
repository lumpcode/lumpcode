# Workspace locks

Path locks and the git-common-dir lock, phase 1 / phase 2 handoff (CLI only).

- **`workspacePathLock`**: single namespace per `path.resolve` (`workspace-path-locks/`); **`workspacePathBusy`** failure; manual `run` `lockMode: 'fail'`, daemon `wait` (15 min then same code + `reason: 'waitTimedOut'`; re-log every 30s); no FIFO v1
- **`run` / `start`** call **`runLumpFromLumpName`** (phase 1) → **`runLumpFromJsConfig`** (phase 2); tests may call `runLumpFromJsConfig` directly with `jsConfig`
- **Phase 1** (dedicated): `preflightDiscoveryBranchWithLock` → load config + disabled soft skip; checkout keeps lock into phase 2; worktree releases after validation (parallel agents across worktrees; shared-git mutations still serialized by `gitCommonDirLock`)
- **Phase 2**: `withWorkspaceLockHooks` — dedicated baseBranch preflight at setup; shared does not call `runProjectPreflight`. Checkout continuous hold; worktree hold execution through setup then release execution-path lock when setup fn returns (branch path lock remains)
- Phase-1 **`releaseLock`** handoff → adopted into `session.releaseExecutionPathLock` at **`runLumpFromJsConfig` entry**; `try/finally` + **`releaseWorkspaceLockSession`** releases on all early returns (including **`tooManyOpenBranches`**)
- Disabled lump soft skip in phase 1 must call **`releaseLock`** before return (phase 2 not invoked)
- **`--discoveryBranch`** on `run` / `lump-plan` / `lump-status` (not on `start`); **`resolveEffectiveDiscoveryBranch`** (discovery only, not `resolvedBaseBranch`); shared: `run` warn-and-ignore, inspect commands honor via `honorDiscoveryBranchOptInShared`
- **`discoverDedicatedLumpsForScanBranch`**: short-lived locked preflight per `scanBranch` with lock holder **`DISCOVERY_SCAN_LOCK_HOLDER`** (`__discovery__`); daemon tick re-runs phase 1 per lump
- **Protocol** (`workspaceFileLock`): each attempt creates its own `<pathHash>.<pid>.<startId>.<token>.lock` with a fresh token, lists the folder, and holds only if its file is the only live one for that path; otherwise it deletes its own file and backs off (wait: jittered poll; fail: 3 looks 20–80ms apart, since a live-looking file may be another contender's attempt). A name belongs to one attempt and is never reused, so lock files are only ever deleted by exact name, and liveness is read from the name, never from content (content is for busy/wait messages)
- **Liveness**: another pid is live if it is running and its `readProcessStartId` matches the name (reused pid = stale; start ids cached 1s per pid but a mismatch is re-read before calling stale; macOS reads `ps` in UTC with a 2s timeout; Windows or no start id: pid only). Same pid (daemon lines share one): live only while the token is in the in-memory `heldTokens` set — added **before** the file is created, removed **after** it is deleted; the set dies with the process
- **Assumptions**: local filesystem (a file created before a listing starts shows in it) and one pid namespace per `~/.lumpcode`; NFS homes or containers sharing `~/.lumpcode` across pid namespaces break pid liveness
- **Tests**: `workspaceFileLock/multiProcess.unit.test.ts` runs several processes × lines through `testing/lockStressWorker.ts` (via vite-node) with a `wx` marker; keep it when changing the protocol
- **v0.10.x compatibility** (one release, ticket `drop-legacy-lock-json`): the sole holder also takes `<pathHash>.lock.json` (temp file + `link`, `wx` fallback, so old readers never see it empty) so old processes see busy; a live or fresh-unreadable (<10s) legacy file counts as busy; a legacy file with our own pid and no token is stale
- `workspaceFileLock` is internal — barrel-export `workspacePathLock` only
- Dead-daemon cleanup: `killDaemonLeftovers` waits up to 2s for the SIGKILLed pid to be gone, then deletes path and git-common-dir lock files named with that pid (`stop --force`, supervisor dead-daemon pass, orphan kill). It is a speed-up, not a safety requirement: any contender deletes a dead owner's file by name
- Do not duplicate core planning in CLI for lock keys (no pre-run `getToDoContextList` or `branchFn`)
